# Календарь звонков


[![hexlet-check](https://github.com/Kamazoh1/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/Kamazoh1/ai-for-developers-project-387/actions)

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

Тестовый стенд на Render: https://call-calendar-xbuh.onrender.com (бесплатный план: после простоя первый запрос идёт около минуты, данные сбрасываются при каждом редеплое и перезапуске)

## Стек

- Бекенд: Python 3.13, FastAPI, uv, pytest, ruff, ty
- Фронтенд: TypeScript, Vite, React, Mantine, oxlint/oxfmt
- Контракт: TypeSpec → OpenAPI → TypeScript SDK (@hey-api/openapi-ts)
- Окружение и задачи: mise, hk (git-хуки), GitHub Actions

```bash

```

### Сквозные тесты (e2e)

Один сценарий Playwright в настоящем браузере: гость бронирует слот, второй гость на тот же слот получает «Это время уже занято», владелец видит встречу в `/admin/bookings`. Подмены сети и часов нет.

```bash
mise run install       # зависимости бэкенда и фронтенда (как для остальных задач)
mise run e2e:install   # один раз: пакет e2e и браузер Chromium
mise run e2e           # поднимает бэкенд на временной SQLite-базе и фронтенд на свободных портах, гоняет сценарий, останавливает всё
```

Задача `e2e` входит в `mise run verify` (после `check`) и не входит в быстрый `mise run check`. В CI один job запускает `mise run verify`, поэтому локальный и CI-прогон совпадают. Воркфлоу `ci.yml` запускается на каждом коммите PR (`pull_request`), в том числе на коммитах агента, и на пуше в `main`. Прогон на `pull_request` проверяет результат слияния PR с `main`. Пуш агента в ветку не создаёт запуск по событию `push`, поэтому только `pull_request` гарантирует CI на коммитах агента. Ветка без PR CI не получает, пока PR не открыт. `hexlet-check.yml` остаётся на `push` и в ветках агента не запускается. Трейс упавшего теста лежит в `e2e/test-results/`.

### Docker

В корне лежит `Dockerfile`: один образ с API и собранным фронтендом (один процесс, один порт). Приложение слушает порт из переменной окружения **`PORT`** (если её нет, то 10000) и стартует само, без аргументов.

```bash
mise run docker:build                  # docker build -t call-calendar .
PORT=8080 mise run docker:run          # http://localhost:8080
mise run docker:smoke                  # собрать образ, запустить на свободном PORT и прогнать браузерный сценарий
```

**Данные после перезапуска.** Брони и типы событий лежат в файле SQLite внутри контейнера (`DATABASE_PATH=/tmp/call-calendar.db`), поэтому **при перезапуске или пересоздании контейнера они сбрасываются**. Чтобы сохранить их, смонтируйте том и укажите путь на нём в `DATABASE_PATH`.

### Деплой на Render

Публичная ссылка: _появится здесь после первого деплоя_.

Сервис описан в `render.yaml` (Blueprint): Docker, бесплатный план, проверка `/health`, порт из `PORT`. На бесплатном плане **нет постоянного диска**: файловая система стирается при каждом редеплое, перезапуске и засыпании сервиса (через 15 минут без запросов), то есть **все данные сбрасываются**. Первый запрос после простоя идёт около минуты.

Создать сервис можно двумя способами:

1. **Через дашборд:** Render → New → Blueprint → выбрать этот репозиторий. Ключ не нужен.
2. **Через MCP-сервер Render:** конфигурация проекта лежит в `.mcp.json`, ключ в репозиторий не попадает.

   ```bash
   # 1. Ключ: https://dashboard.render.com/u/settings → API Keys → Create API Key.
   # 2. Положите его в переменную окружения до запуска Claude Code (не в файл репозитория):
   read -rs RENDER_API_KEY && export RENDER_API_KEY
   # 3. Запустите Claude Code из корня репозитория и подтвердите проектный MCP-сервер «render».
   claude
   ```

   Ключ Render действует на весь аккаунт: не публикуйте его и не вставляйте в чат. `.env*` игнорируется git.

Проверить опубликованное приложение тем же браузерным сценарием (гость записывается, второй гость получает отказ, владелец видит встречу):

```bash
mise run e2e:url -- https://<имя-сервиса>.onrender.com
```

Сценарий создаёт тип события и бронь в работающем приложении; они пропадут при следующем перезапуске.

### Релизы

Релизы собирает [release-please](https://github.com/googleapis/release-please) из Conventional Commits. Версия одна на весь репозиторий; тег выглядит как `v0.2.0`.

1. После каждого влития в `main` workflow `release-please.yml` открывает (или обновляет) release PR с заголовком вида `chore(main): release 0.2.0`. В нём обновлённый `CHANGELOG.md` и новая версия в `backend/pyproject.toml`, `backend/uv.lock`, `frontend/package.json`, `frontend/package-lock.json`. Версия, с которой release-please считает следующую, хранится в `.release-please-manifest.json`.
2. Версию определяют типы коммитов с прошлого релиза: `fix:` даёт патч, `feat:` — минор (пока версия `0.x`), `!` или `BREAKING CHANGE:` — мажор. Коммиты `chore:`, `docs:`, `ci:` в changelog не попадают и релиз сами не открывают.
3. CI на release PR не запускается: ветку создаёт `GITHUB_TOKEN`, а события от него GitHub не превращает в запуски workflow. Поэтому перед слиянием проверьте ветку вручную, чтобы убедиться, что lock-файлы с новой версией ставятся и всё зелёное:

   ```bash
   git fetch origin release-please--branches--main--components--call-calendar
   git checkout -B release-check FETCH_HEAD
   mise run install && mise run verify
   git checkout main && git branch -D release-check
   ```

4. Слияние release PR создаёт тег и релиз на GitHub с этим changelog. Вручную версии и changelog править не нужно.

Для работы в настройках репозитория (Actions → General) должна быть включена опция «Allow GitHub Actions to create and approve pull requests».

### Агент по `@claude`

Воркфлоу `.github/workflows/claude.yml` запускает [claude-code-action](https://github.com/anthropics/claude-code-action) по комментарию с `@claude` в issue, PR или ревью PR.

- **Событие.** `issue_comment` и `pull_request_review_comment` с `types: [created]`, `pull_request_review` с `types: [submitted]` (у ревью нет типа `created`, `submitted` — тот же момент).
- **Модель.** `claude-sonnet-5-5` (последний Sonnet), задана явно через `--model` в `claude_args`. Ключ лежит в GitHub Secrets: `CLAUDE_CODE_OAUTH_TOKEN`. Менять модель нужно в `claude.yml`.
- **Назначение.** Выполнить задачу из комментария по правилам из `AGENTS.md`: Conventional Commits, контракт `api/main.tsp` меняется первым, перед пушем зелёный `mise run check`. Скиллы (`.claude/skills`) и `docs/agents/` берутся из `main`, инструменты ставятся тем же `mise`, что и в `ci.yml`.
- **Результаты.** Ответный комментарий от `claude[bot]` в том же issue или PR; если задача требует правок, ветка и PR от приложения; прогон виден во вкладке Actions (workflow `claude`).
- **Кто может вызвать.** Только человек (`user.type == 'User'`) с `author_association` `OWNER`, `MEMBER` или `COLLABORATOR`. Комментарии ботов, в том числе ответы агента-ревьюера, правку не запускают: код агент меняет только по команде человека. Воркфлоу обрабатывает только события комментариев; ревью PR делает `review.yml`. Репозиторий публичный, но форки секретов не получают: воркфлоу работает в контексте основной ветки, код из форка не выполняется.
- **Права и ограничения.** У `GITHUB_TOKEN`: `contents: write`, `pull-requests: write`, `issues: write` (комментарии, ветки и PR), `id-token: write` (обмен OIDC на токен приложения) и `actions: read` (чтобы агент читал результаты CI). Тайм-аут задания 30 минут, один прогон на issue или PR одновременно (новый комментарий ждёт). Агенту разрешены `mise run`, `gh pr`, `gh issue` и `git`.
- **Установка.** Нужно приложение [Claude](https://github.com/apps/claude) на репозитории и секрет `CLAUDE_CODE_OAUTH_TOKEN` (оба настраивает `/install-github-app`).

**Набор команд (mentions).** Агент понимает свободный текст, но в проекте используются три формы:

| Комментарий | Что делает агент |
|---|---|
| `@claude explain this issue` | объясняет issue или PR, ничего не меняет |
| `@claude implement this` / `@claude fix <что>` | правит код, прогоняет `mise run check`, открывает PR |
| `@claude review this PR` | читает дифф и результаты CI, отвечает комментарием |

**Share.** Сессии агента не публикуются: `show_full_output` и `display_report` не включены (в действии они по умолчанию `false`, в `claude.yml` не заданы). Репозиторий публичный, а полный вывод и отчёт содержат результаты инструментов (пути, окружение), поэтому включать их не нужно. Остаются только комментарий агента и ссылка на прогон в Actions.

### Автотриаж issues

Воркфлоу `.github/workflows/triage.yml` разбирает новые issue по правилам скилла `triage` и словарю меток из `docs/agents/triage-labels.md`.

- **Событие.** `issues` с `types: [opened]`. Событий `edited` и `labeled` нет: изменения меток самим агентом не должны запускать его снова.
- **Кто запускает.** Только авторы `OWNER`, `MEMBER` и `COLLABORATOR`, боты исключены. Текст issue считается недоверенным: агент читает его как данные и не выполняет написанные там инструкции.
- **Что не разбирается повторно.** Issue, у которого уже есть метка состояния (`needs-*`, `ready-for-*`, `wontfix`), пропускается. Тикеты, подготовленные скиллами (`to-tickets` публикует их сразу с `ready-for-agent`), поэтому повторно не разбираются. Вторая проверка в prompt: если под issue уже есть комментарий, начинающийся с `> *This was generated by AI during triage.*`, агент ничего не меняет.
- **Что делает агент.** Ставит одну категорию (`bug` или `enhancement`) и `needs-triage`, оставляет один комментарий с рекомендацией (категория, предлагаемое состояние, что в коде относится к делу, нет ли уже реализации). Issue не закрывает и `ready-for-agent`, `ready-for-human`, `wontfix` не ставит: решение остаётся за maintainer'ом.
- **Модель и prompt.** `claude-haiku-5-5` (триажу хватает), prompt задан в `triage.yml`. Ключ: `CLAUDE_CODE_OAUTH_TOKEN` в GitHub Secrets.
- **Ограничения.** Тайм-аут 10 минут, не более 15 шагов агента. Один прогон на issue (`concurrency` по номеру issue): общая группа на все issue оставляла бы в очереди только один запуск, а остальные отменялись бы. Права `GITHUB_TOKEN`: `contents: read`, `issues: write`, `id-token: write`. Агенту разрешены чтение репозитория и `gh issue view`, `gh issue comment`, `gh issue edit`; `git`, `mise` и правка файлов недоступны.
- **Метки.** `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` должны существовать в репозитории (создаются через `gh label create`, см. `docs/agents/triage-labels.md`).
- **Share.** Как и у `@claude`, сессия не публикуется.

### Авторевью PR

Воркфлоу `.github/workflows/review.yml` делает независимое ревью pull request: отдельный прогон агента, который видит только дифф и критерии из `REVIEW.md`, а не сессию автора кода. Он только комментирует: не одобряет, не требует правок, не пушит.

- **Событие.** `pull_request` с `types: [opened, synchronize, reopened, ready_for_review]`.
- **Кого ревьюит.** PR из веток этого же репозитория от доверенного автора: человека с правом записи (`OWNER`, `MEMBER`, `COLLABORATOR`) или самого приложения (`claude[bot]`). PR агента получают ревью наравне с остальными, поэтому ботов по типу воркфлоу не отсекает. Пропускаются черновики, PR из форков и PR release-please (`release-please--*`, там только версии и changelog).
- **Форки.** Обычный `pull_request`: PR из форка не получает секрет модели, поэтому воркфлоу его пропускает. `pull_request_target` (секреты вместе с кодом из PR) не используется, код форка не запускается. Такой PR проверяет человек.
- **PR агента и боты.** Когда интерактивный агент (`claude.yml`) пушит в ветку PR, событие приходит от `github-actions[bot]`, а действие по умолчанию отказывает запускам от ботов. Поэтому в `review.yml` задано `allowed_bots: "claude,github-actions"`; без этого ревью PR агента падало с `non-human actor`. Границу доверия задаёт условие `if` (своя ветка, доверенный автор), а не список ботов.
- **Критерии.** `REVIEW.md`: контракт `api/main.tsp` первым, термины `GLOSSARY.md` и ADR, тесты, секреты и безопасность, процесс (Conventional Commits, шаблон PR, `hexlet-check.yml`), формат ответа. Агент читает файл из базовой ветки (`git show <base.sha>:REVIEW.md`), поэтому PR не может ослабить собственное ревью. Правки `REVIEW.md`, `AGENTS.md`, `.github/workflows/` и `skills-lock.json` помечаются как требующие внимания. Линтеры, типы и тесты агент не повторяет: их запускает CI.
- **Результат.** Один сводный комментарий от `claude[bot]` (`use_sticky_comment`: он обновляется при каждом пуше, новые не копятся) с вердиктом `blockers / concerns / nits` и находками с `file:line`; строчные комментарии только для замечаний к одной строке. Сам прогон виден в Actions (workflow `review`). Ревью не блокирует слияние: решает человек.
- **Модель и prompt.** `claude-opus-5-5`, отличается от `claude-sonnet-5-5`, на которой работает `@claude`, поэтому код и ревью делают разные модели. Prompt лежит в `review.yml`. Описание, заголовок и комментарии PR агент считает данными и инструкциям из них не следует.
- **Права и ограничения.** `contents: read`, `pull-requests: write`, `id-token: write` и `actions: read` (чтобы считать прошлые прогоны), у checkout `persist-credentials: false`. Тайм-аут 15 минут, не более 25 шагов агента. `concurrency` по номеру PR с `cancel-in-progress: true`: новый пуш отменяет устаревшее ревью и запускает новое. Агенту разрешены чтение репозитория, `git show|diff|log`, `gh pr view|diff|comment` и строчные комментарии; правка файлов, `git commit` и `git push` запрещены явно (`--disallowedTools`).
- **Предел запусков на PR.** До вызова модели шаг `Check the review limit of this PR` запускает `.github/scripts/review_limit.py` и считает завершённые прогоны `review` этого PR (успешные и упавшие; пропущенные, отменённые новым пушем, идущие и текущий не считаются). Когда они исчерпаны, шаг один раз на коммит пишет в PR комментарий с причиной, head SHA и ссылкой на логи, добавляет то же в сводку задания и падает: шаг с моделью не запускается, а проверка `review` красная, чтобы непроверенный коммит не выглядел проверенным. Предел задаёт переменная репозитория `REVIEW_MAX_RUNS_PER_PR` (Settings → Secrets and variables → Actions → Variables); если её нет или значение не число больше нуля, действует 5. Чтобы получить ещё одно ревью, поднимите значение и перезапустите проверку или запушьте коммит. Скрипт берётся из базовой ветки, поэтому PR не может поднять собственный предел; в самом PR, который его добавляет, шага ещё нет в базе, и он пропускается. Логика покрыта тестами `backend/tests/test_review_limit.py` (их запускает `mise run test`).
- **Ограничение действия.** Обмен OIDC-токена на токен приложения проверяет, что файл воркфлоу совпадает с версией в основной ветке. Поэтому PR, который сам меняет `review.yml`, ревью не получит, пока изменение не влито.
- **Share.** Как и у других агентов, сессия не публикуется.

### Независимая браузерная проверка

Воркфлоу `.github/workflows/browser-check.yml` отдельно от `ci.yml` и на отдельном раннере собирает приложение с нуля, гоняет настоящий бэкенд и фронтенд в Chromium (`mise run e2e`) и оставляет артефакт с результатом и точным head SHA PR. Секретов не использует, `pull_request_target` нет, поэтому PR из форка её запустить может безопасно.

- **Сценарии.** Тег в названии теста Playwright говорит, зачем он: `@main` — сценарий фичи, которую приносит PR; `@adjacent` — соседний сценарий, который должен продолжать работать (сейчас это гонка двух гостей за слот в `e2e/tests/booking.spec.ts`). Для PR с заголовком `feat…` нужны оба и оба должны пройти, для остальных нужен проходящий `@adjacent`. Проваленный сценарий, отчёт без сценариев или `feat` без `@main` дают красную проверку и вердикт `fail` с причинами.
- **Артефакт.** `browser-check-<head sha>` с `result.json` (вердикт, причины, сценарии со статусами и тегами, `head_sha` PR, `merge_sha` того, что реально тестировалось, ссылка на логи), сырым отчётом Playwright и трейсами упавших тестов (`e2e/test-results/`). Хранится 30 дней. Артефакт остаётся и у красной проверки.
- **Решение о мерже.** Перед слиянием человек запускает `mise run browser-check:verify -- <номер PR>`. Скрипт берёт текущий head и заголовок PR, скачивает артефакт именно для этого head и отказывает, если артефакта нет, он относится к другому коммиту (в сообщении оба SHA) или проверка не пройдена. Так артефакт, снятый до последнего пуша агента, мержу не помогает. Вердикту из самого артефакта скрипт не верит: его считал код самого PR, а заголовок мог измениться после прогона. Поэтому вердикт пересчитывается копией скрипта из базовой ветки по сырому отчёту Playwright (`playwright-report.json` в артефакте) и текущему заголовку. Если PR меняет саму проверку (`browser_check.py`, `browser-check.yml`, `e2e/playwright.config.ts`), скрипт печатает предупреждение: артефакт получен PR'овской версией проверки, эти правки нужно прочитать до решения.
- **Ограничения.** Тайм-аут 20 минут, `concurrency` по номеру PR с отменой устаревшей проверки: новый пуш отменяет её, потому что её артефакт нёс бы устаревший SHA. Права `contents: read`. Логика сборки результата, пересчёта вердикта и сверки SHA покрыта тестами `backend/tests/test_browser_check.py`; скрипты из `.github/scripts` проверяет линтер (`mise run lint`).

### Шаблон PR

`.github/pull_request_template.md` подставляется в описание каждого нового PR и повторяет разделы, которые проверяет `REVIEW.md`:

- **Summary:** что и зачем, со ссылкой на тикет (`Closes #N`).
- **Checks:** чек-лист (`mise run verify`, контракт и `mise run generate`, тесты, браузерная проверка на текущем head, глоссарий и ADR, нет секретов) и **Evidence** (вывод тестов, скриншот, запрос и ответ).
- **Risk:** дверь (`one-way` или `two-way`) и радиус поражения.
- **Rollback:** как откатить (`git revert`, флаг, правка данных) и что останется после отката.

### Настройки репозитория для агентов

Что должно быть включено в GitHub, чтобы три агента (`claude`, `triage`, `review`) работали:

1. Приложение [Claude](https://github.com/apps/claude) установлено на репозиторий (`/install-github-app`).
2. Секрет `CLAUDE_CODE_OAUTH_TOKEN` в Settings → Secrets and variables → Actions.
3. Метки `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` (см. `docs/agents/triage-labels.md`).
4. Settings → Actions → General: опция «Allow GitHub Actions to create and approve pull requests» (для release-please).
5. Сводка по агентам (браузерная проверка `browser-check.yml` без модели, её описание выше):

| Воркфлоу | Событие | Кто запускает | Модель | Тайм-аут | Параллельность |
|---|---|---|---|---|---|
| `claude.yml` | комментарий с `@claude` | человек: `OWNER`, `MEMBER`, `COLLABORATOR` | `claude-sonnet-5-5` | 30 мин | один на issue или PR, новый ждёт |
| `triage.yml` | новый issue | те же, не боты, без меток состояния | `claude-haiku-5-5` | 10 мин | один на issue |
| `review.yml` | PR из этого репозитория | автор: человек с правом записи или `claude[bot]`; не черновик, не форк | `claude-opus-5-5` | 15 мин | один на PR, устаревший отменяется; не более `REVIEW_MAX_RUNS_PER_PR` (5) ревью на PR |
