# Bookings never overlap: checked and inserted in one write-locked transaction

Two bookings never overlap, whatever their event types: intervals are half-open `[start, end)`, so 10:00–11:00 blocks 10:30–11:00 but allows 11:00. A booking is created by checking for overlaps and inserting in a single SQLite transaction that takes the write lock up front (`BEGIN IMMEDIATE`), so concurrent requests, even from several server processes, are serialized; the loser gets `409 slot_taken`. A request that cannot get the lock within 30 seconds gets `503`. We rejected occupancy cells with a `UNIQUE` key: the database would enforce the rule itself, but the schema would be tied to the 30-minute start step and changing the step would need a data migration. The cost of our choice is that the guarantee lives in code order rather than in a database constraint, so it is covered by acceptance tests over HTTP on a file-based database: 10 parallel requests for one slot give exactly one success, overlapping intervals of different types give exactly one, adjacent intervals both succeed.
